# Harness² structured-step trial investigation — 2026-10-19

## Frame and context

Expected: on one development step task, Harness² edits guidance, tests proposals, selects a development-valid candidate, then a frozen candidate is compared on held-out tasks against fixed and one-feedback baselines. Parent reports 51 calls in `evidence/dance-step-h2-v1.json`: development `inv1` and `dom1` pass, `c1` fails, yet k=1 selects `c1`; held-out E2B fixed/repair 2/8, adapted 1/8, and Qwen 2/8 throughout. This matters because a successful intermediate proposal is not evidence of a successful final harness or held-out generalization. The new adapter is uncommitted; the task compiler entered recent Git history at `c293f2e`. Preserve all run evidence. This investigation only adds this note, without provider calls or source changes.

## Competing hypotheses and diagnostic tests

1. **Upstream selection follows delivery rather than host validity.** Inspect actual `run_domain` k=1 schedule/selector code and saved summary/selection receipts. If `c1` has a proposal file but an invalid verdict and the selector still chooses it, delivery-only admission explains the development selection. If selector checked verdict validity or chose another run, this hypothesis is false.
2. **Adapter or runner mis-scored an otherwise valid composition.** Recompute every raw proposal with frozen `parse_steps`, `compile_steps`, `compile_task`, and `verify_task` using the saved task. Compare exact reasons and acceptance against saved receipts, including the `c1` result. Disagreement supports a bug or source drift; exact replay weakens it.
3. **Development feedback or editor context leaked answers or went stale.** Trace all three editor requests and their included files/rollouts, then hash/compare final guidance and timestamps/order before evaluation. If held-out tasks, enumerated feasible plans, or post-evaluation results appear in editor context, or candidate changed after freeze, leakage/staleness is supported; clean boundaries weaken it.
4. **Fixture or evidence bookkeeping mismatch.** Recompute all source hashes, validate fixture feasibility and development task legality, tally the 51 calls, native completion/tokens/cost and run paths. If hashes, call indices, or user task facts differ from the current sources/receipts, outcomes cannot be attributed cleanly. Exact agreement weakens this hypothesis.
5. **The final composition genuinely differs from successful intermediates but lacks generalization.** Compare the actual `inv1`, `dom1`, and `c1` guidance texts, their development raw replies and host reasons, and held-out responses for the frozen final candidate. A failing `c1` despite passing intermediates proves a local composition regression; held-out scores show only this final candidate's transfer, not intermediate transfer.

## Assessment and bounded next step

The evidence supports a narrow failure mechanism with high confidence: the final composed guidance produced an invalid development plan, while generic Harness² k=1 selection admitted it because it delivered a proposal, and the final guidance did not improve these within-family evaluation cases. Source drift, malformed output, fixture illegality, and oracle leakage are unsupported by the replay. The one-development-task selection and one response per evaluation condition cannot show that `inv1` or `dom1` would transfer; testing either on these now-observed cases would be exploratory reuse, not fresh held-out validation.

For a next predeclared run, add a **host-owned development admission step after each rollout and before freezing evaluation guidance**. Read each immutable development verdict and guidance hash; among bounded candidates, retain a host-valid intermediate by a fixed priority (for example, valid final, then latest valid intermediate, then valid base), and record when no candidate qualifies. Do not overwrite the upstream selection record; save the host admission decision separately. Freeze that choice before touching a new independent evaluation set, then compare it at matched call budgets against fixed guidance and bounded repair, with first/final success, abstention, calls, tokens, and cost separate. This would test whether retaining a valid intermediate avoids this observed final-stage loss; it would not make development validity a guarantee of held-out gain.

The preceding observation that the third editor request lacked intermediate guidance/rollouts could arise from two distinct places. **Hypothesis A:** upstream never staged these files in compose context, so the omission is intrinsic to this k=1 composition setup. **Hypothesis B:** upstream staged them but our `ProductionImprover` context collector selected too few paths, so it is an integration omission. **Hypothesis C:** files were staged and collected, but the provider request or receipt omitted them later. Discriminate with three read-only checks: (1) list the exact compose context directory and relative paths, hashes, sizes, and contents for `inv1`/`dom1` candidate harnesses, rollouts, and verdicts; (2) compare those paths to `collect_context` source and to the third editor receipt's `included_files` plus exact provider user text; (3) inspect upstream compose context construction and mission for its intended evidence. Then identify the smallest adapter-specific, bounded, development-only collector/proposer change that would pass useful candidate text and host verdicts without held-out tasks or host oracle plans. Do not change source or call providers during this addendum.
