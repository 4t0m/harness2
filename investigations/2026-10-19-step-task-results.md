## Competing hypotheses and discriminating checks

1. **Model constraint-planning failure.** Exact raw plans are legal, but choices violate final target, lane, or required slots. Replay all responses through `parse_steps`, `compile_steps`, and `compile_task`; classify each error using host task facts. If raw JSON and frozen compilers agree with receipt errors, this is supported. If legal task-satisfying raw plans fail the compiler, it is ruled out as the primary cause.
2. **Runner, fixture, or task/prose mismatch.** The model may receive different requirements than the host checks, or the runner may score a different field/response. Compare each case's prose, structured task, messages, native response content, recorded content, and posthoc verdict; independently enumerate feasible plans. A contradiction, oracle leak, or raw/recorded mismatch supports this; exact agreement weakens it.
3. **Invalid format/interface rather than task reasoning.** Outputs may use unknown identifiers, malformed JSON, extra fields, or wrong schema despite the prior clarified contract. Count syntax/type/identifier failures separately from semantic task failures. Predominantly malformed responses support this; parseable legal plans with constraint violations rule it out as the main mechanism.
4. **Ineffective or misleading correction.** The feedback may omit the actual violated public constraint, disclose hidden answers, or elicit the same response. Trace every fallback message and before/after raw output, ensuring each cited constraint exists in the task. Useful feedback with changed but still invalid plans points to planning difficulty; repeated identical output or incorrect feedback points to the correction interface.
5. **Source drift, partial evidence, or accounting error.** Recompute every recorded source SHA-256; check completion, call count, model/case/attempt coverage, native tokens/durations and wall latency. Drift or missing rows prevents attributing outcomes to the current compiler; matching hashes and replayed counts rule this out.

## Assessment and next test design

The dominant observed failure is model selection of legal but task-invalid choices under a clear structured contract. Confidence is high for that narrow conclusion because raw/native equality, unchanged source hashes, independent compiler replay, and exact fixture preflight agree. The evidence weakens the runner/parser, malformed-interface, and fixture-contradiction hypotheses. It does not isolate why the models overlooked constraints, whether a different feedback message would help, or whether success would transfer to new task families.

The host's deterministic `feasible_plans` already enumerates every valid plan in at most 256 combinations and supplied 72 verified solutions for these eight supported tasks. Thus this trial measures **delegating a tiny constraint search to a model**, not whether a model is necessary to solve it. A deterministic solver is the appropriate task-success baseline and would dominate these 5/16 final model successes on the current interface. For meaningful Harness² development, freeze these 12 cases as observed development data, run any prompt adaptation only there, and compare a fixed prompt, one bounded public-feedback correction, and an adapted Harness² guidance candidate at matched model/call budgets. Evaluate the frozen candidate on genuinely new task families/constraint combinations and impossible cases, with feasibility and acceptance still host-owned; report first-pass, final, false acceptance, abstention, calls, and tokens separately. Include the deterministic solver's 100% feasibility baseline. If the goal is to test where a model adds value, use new natural-language briefs requiring interpretation into a host-checked task representation, then let deterministic code do exact plan search; keep the independent structured oracle out of model-editable prompts and do not claim success on structured constraint enumeration is an avatar-quality result.
