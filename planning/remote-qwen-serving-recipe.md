# Qwen3.6-35B-A3B single-5090 serving recipe

**Research date:** 2026-10-19
**Status:** researched deployment plan; not run or independently tested.

## Recommendation

For a bounded text-only 30-minute trial on one incoming RTX 5090, use NVIDIA's NVFP4 checkpoint with the vLLM 0.28.0 Docker release and the official vLLM RTX 5090 overrides. This is the concrete path the current upstream recipe marks for the 5090: the variant needs at least 21 GB VRAM, uses tensor parallelism 1, and names `vllm/vllm-openai:v0.28.0`. The official Qwen FP8 checkpoint is listed at 42 GB minimum and single H100/H200, so it is not the fit for a 32 GB 5090. [vLLM Qwen3.6 recipe](https://raw.githubusercontent.com/vllm-project/recipes/main/models/Qwen/Qwen3.6-35B-A3B.yaml)

Pin the NVFP4 repository to commit `6c7f09d4036e97393f82e9f9ecd1a5c35ca5ee92`. At that revision Hugging Face reports 23.5 GB total, with three model shards of 10 GB, 10 GB, and 3.41 GB. The repository is Apache-2.0 licensed. [Pinned NVIDIA checkpoint tree](https://huggingface.co/nvidia/Qwen3.6-35B-A3B-NVFP4/tree/6c7f09d4036e97393f82e9f9ecd1a5c35ca5ee92)

Use the exact AMD64 CUDA 12.9 image `vllm/vllm-openai:v0.28.0-x86_64-cu129-ubuntu2404`, manifest digest `sha256:a77ed1c057e0458dbed205dea0ecaacd0ca2405721be6e58182bf9ee42c359f6` (linux/amd64; 10.17 GB compressed). This pins the platform-specific image directly. It is the CUDA 12.9 v0.28.0 build, while the recipe's default tag is a CUDA 13 build; the vLLM version and 5090 overrides match, but this exact CUDA 12.9 image variant is source-checked rather than independently launched. [AMD64 image manifest](https://hub.docker.com/layers/vllm/vllm-openai/v0.28.0-x86_64-cu129-ubuntu2404/images/sha256-a77ed1c057e0458dbed205dea0ecaacd0ca2405721be6e58182bf9ee42c359f6)

## Launch command

This trial has no persistent volume. Keep the Hugging Face cache on the pod's ephemeral container disk; assume the 23.5 GB checkpoint must be fetched on each allocation. For the in-pod authenticated gate on public 8080 and vLLM bound to loopback on 8000, use a temporary private RunPod template: REST v1 template creation supports `dockerEntrypoint` and `dockerStartCmd`; place the small stdlib Python gate/launcher inline as a `python3 -c` entrypoint and keep the vLLM model/flags in the start command. Do not put credentials in the template; pass them as pod-only environment values. Set template `volumeInGb` to **0** explicitly: REST v1 `TemplateCreateInput` defaults it to 20 GB when omitted. Before renting, GET the template by ID and verify `isPublic:false`, pinned image, entrypoint, start command, and `volumeInGb:0`. GraphQL pod creation accepts both `templateId` and `terminateAfter`; set the latter to the absolute UTC allocation deadline. This uses REST v1 templates, which RunPod has deprecated for retirement on 2026-11-15, but avoids a custom image build/pull. [REST v1 template API](https://docs.runpod.io/api-reference/templates/POST/templates), [REST v1 template schema/defaults](https://rest.runpod.io/v1/openapi.json), [GraphQL pod-create input](https://graphql-spec.runpod.io/)

The `dockerStartCmd` stored in the template should be this JSON argument array (the launcher runs `vllm serve` with these arguments):

```json
["nvidia/Qwen3.6-35B-A3B-NVFP4", "--revision", "6c7f09d4036e97393f82e9f9ecd1a5c35ca5ee92", "--tensor-parallel-size", "1", "--quantization", "modelopt_fp4", "--kv-cache-dtype", "fp8", "--block-size", "128", "--moe-backend", "marlin", "--attention-backend", "flashinfer", "--attention-config", "{\"use_trtllm_attention\":true}", "--gpu-memory-utilization", "0.85", "--max-model-len", "4096", "--max-num-seqs", "1", "--max-num-batched-tokens", "4096", "--language-model-only", "--host", "127.0.0.1", "--default-chat-template-kwargs", "{\"enable_thinking\":false}"]
```

Set `VLLM_HAS_FLASHINFER_CUBIN=1` in the pod environment. Set `HF_HOME` to a container-disk path. In the template, make the entrypoint array `python3`, `-c`, and the reviewed inline launcher source. The launcher should run the vLLM child with the argument array, then start the authenticated allowlist gate; expose only 8080/http, never 8000.

This uses the 5090 recipe's model-opt FP4 quantization, FP8 KV cache, block size 128, Marlin MoE backend, FlashInfer attention/TRT-LLM attention, 0.85 GPU memory utilization, and cubin environment setting. It reduces context from the recipe's 65,536 to 4,096 tokens and concurrency from 8 sequences to 1 for the small serial text task. `--language-model-only` skips the vision encoder because this trial sends text only. MTP/speculative decoding is intentionally omitted: it is opt-in in the recipe and is not needed to test one short request at a time. These reductions are trial settings, not a performance claim. [Official 5090 overrides and opt-in features](https://raw.githubusercontent.com/vllm-project/recipes/main/models/Qwen/Qwen3.6-35B-A3B.yaml)

Before launching, verify `nvidia-smi` reports an RTX 5090 and a Linux driver at least 580. This is a conservative target for the CUDA 12.9/13.x vLLM container builds. [NVIDIA CUDA compatibility table](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

## Readiness, API, and output control

The cap is 30 minutes from allocation, including image transfer, weight download, startup, and calls. The checkpoint is 23.5 GB and the exact container manifest reports 10.17 GB compressed: at least 33.67 GB must be transferred before counting custom-image overhead, metadata, extraction, and startup. This requires an idealized average of about 18.7 MB/s (150 Mbps) over the entire 30 minutes; no source promises this throughput or a warm cache. Treat a cold allocation as a feasibility trial, and abort early if the server is not ready by the predeclared cutoff. There is no persistent volume/cache to reduce this uncertainty. Readiness is verified through the gate's authenticated allowlisted health/model routes before submitting any trial request. [pinned model files](https://huggingface.co/nvidia/Qwen3.6-35B-A3B-NVFP4/tree/6c7f09d4036e97393f82e9f9ecd1a5c35ca5ee92), [AMD64 image manifest](https://hub.docker.com/layers/vllm/vllm-openai/v0.28.0-x86_64-cu129-ubuntu2404/images/sha256-a77ed1c057e0458dbed205dea0ecaacd0ca2405721be6e58182bf9ee42c359f6)

Qwen3.6 enables thinking by default. Disable it for this bounded direct-output task with the server default above. For OpenAI-compatible `POST /v1/chat/completions`, send the served model name, a user message, a small `max_tokens` (for example 128), and, when the runner has a schema, vLLM's Chat Completions `response_format: {"type":"json_schema","json_schema":{"name":"intent","schema":...}}`. vLLM 0.28 documents this exact response-format shape. Keep schema validation and task acceptance in the trusted runner; constrained output is not an acceptance oracle. [Qwen thinking controls and OpenAI-compatible endpoint](https://huggingface.co/Qwen/Qwen3.6-35B-A3B), [vLLM structured outputs](https://docs.vllm.ai/en/v0.28.0/features/structured_outputs/)

The `VLLM_API_KEY` environment variable protects common `/v1` routes, but vLLM explicitly warns that other endpoints remain unauthenticated, including `/invocations`. Only expose the narrow authenticated gate on 8080; do not publish vLLM's port 8000. The gate must allowlist the exact required methods/routes and keep upstream 8000 bound to `127.0.0.1`. [vLLM security guide](https://docs.vllm.ai/en/latest/usage/security/), [vLLM 0.28 serve CLI security warning](https://docs.vllm.ai/en/v0.28.0/cli/serve/)

## RunPod create and termination path

The documented cross-route composition is REST v1 private template creation with `dockerEntrypoint`/`dockerStartCmd`, then GraphQL `podFindAndDeployOnDemand` with `templateId` and ISO UTC `terminateAfter`. The REST v1 template schema defaults `volumeInGb` to 20, so set it to 0 and verify the readback; otherwise this would silently violate the no-persistent-volume constraint. The current GraphQL input has no entrypoint override; current REST v2 create has no entrypoint or deadline field. RunPod CLI v2.12 removed `--stop-after` and `--terminate-after`, so do not copy those options from older docs. [REST v1 template API](https://docs.runpod.io/api-reference/templates/POST/templates), [GraphQL schema](https://graphql-spec.runpod.io/), [REST v1 deprecation](https://github.com/runpod/docs/blob/main/api-reference/overview.mdx), [current v2 create implementation](https://github.com/runpod/runpod-python/blob/main/runpod/api/ctl_commands.py), [CLI v2.12 change](https://github.com/runpod/runpodctl/commit/51ca7f0)

For an in-pod gate, create a private template before the trial, read it back by ID to verify its entrypoint/start command and ensure it contains no secret or persistent volume, then use GraphQL creation with that `templateId` and `terminateAfter` set to allocation plus 30 minutes. GraphQL pod output gives the `templateId` but not the saved deadline. At runtime, query the pod with template details and confirm the stored configuration; keep an independent client-side watchdog that invokes the provider termination API before the cap and then verifies provider state. Container exit or `podStop` is not sufficient evidence of billing termination. The exact cross-route inheritance and scheduled firing have not been tested. Delete the temporary template after the pod is terminated. See [RunPod create/deadline investigation](../investigations/2026-10-19-runpod-create-deadline.md).

## Evidence boundary and open checks

This is a source-backed serving recipe, not an executed 5090 deployment. The pinned AMD64 CUDA 12.9 digest is resolved; the private-template plus GraphQL-create combination is schema-backed but not trialed. The vLLM recipe marks RTX 5090 and RTX PRO 6000 profiles verified; this plan uses the 5090 profile with 4K context and single concurrency. It does not establish cold-start time, cache state, throughput, host-driver compatibility, cross-route template inheritance, or exact deadline firing. For the $5 inclusive cap, parent must check the live GPU quote and include allocation, storage, and any transfer charges before launch.

At launch, confirm the image pulls for `linux/amd64`, confirm the host driver is at least 580, then check the server log and readiness endpoints. If the short trial starts from a cold cache, treat readiness time as a feasibility result rather than assuming the model will be available for 30 minutes of calls. No model weights or container images were downloaded during this research.


## Executable trial contract

`experiments/motif_runpod_trial.py` owns one allocation attempt, with no replacement hardware or repeated allocation after an ambiguous response. It refreshes price/account state, verifies a temporary private template, requests provider deletion at allocation-request time plus 30 minutes, starts local deletion by minute 25, and stops waiting for readiness at minute 18. Eight existing compact motif cases run without corrections; if all compile, a finite three-minute local viewer can use the same remote model. Correctness is scored separately from valid structure. The planned $5 ceiling is an operational budget, not a RunPod-enforced account limit: the controller records the actual hourly rate plus a conservative separate disk estimate and verifies deletion by pod ID. Exact billed cost requires billing evidence.

The pod runs `motif_pod_gate.py` as its entrypoint and launches vLLM directly as a child in the same container. The checkpoint is fixed and served under alias `qwen`. Only port 8080 is exposed, with token authentication and a route allowlist; vLLM itself binds loopback. The gate is capped at 24 calls and 128 output tokens per call. There is no HTTP log route. Startup diagnostics are redacted for the two ephemeral tokens and emitted into the provider's existing authenticated management logs; overlong log lines are omitted. The RunPod account key is never supplied to the pod.

Before allocation: 15 remote-provider/viewer/transport tests, five gate tests, four simulated lifecycle tests, and eight runner fixture replays passed. These are offline infrastructure checks, not model or GPU execution. The real trial must preserve its own receipt and failures.
